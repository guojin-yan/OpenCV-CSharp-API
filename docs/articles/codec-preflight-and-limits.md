# Codec Preflight And Limits / 编解码预检与限制

The buffer and owner decisions for a future writer API are recorded in the [Codec Buffer And Owner ADR](codec-buffer-and-owner-adr.md). The current public encode path remains the existing `byte[]` contract.

未来 writer API 的缓冲区和 owner 决策记录在[编解码缓冲区与所有权 ADR](codec-buffer-and-owner-adr.md)中。当前公开编码路径仍是现有 `byte[]` 契约。

On Span-capable target frameworks, the preview writer overload writes the native encoded result into an `IBufferWriter<byte>` and advances it once. It does not retain the writer or its memory:

```csharp
var destination = new System.Buffers.ArrayBufferWriter<byte>();
Cv2.ImEncodeTo(".png", image, destination);
ReadOnlySpan<byte> encoded = destination.WrittenSpan;
```

在支持 Span 的目标框架上，preview writer overload 将 native 编码结果写入 `IBufferWriter<byte>`，并只调用一次 `Advance`；不会保留 writer 或其内存。

Cv2.Identify performs a managed header inspection before native decoding. It recognizes common PNG, JPEG, JPEG 2000 (raw J2K and JP2), AVIF, GIF, WebP, BMP, Sun Raster, Radiance HDR, OpenEXR, TIFF, and PNM signatures, reports dimensions when the header proves them, and never opens the native runtime. It is intended for admission control and diagnostics, not for claiming that a file is valid or that every codec feature is available.

Cv2.Identify 会在 native 解码前执行 managed 头检查。它识别常见的 PNG、JPEG、JPEG 2000（原始 J2K 与 JP2）、AVIF、GIF、WebP、BMP、Sun Raster、Radiance HDR、OpenEXR、TIFF 和 PNM 签名，在头部能够证明时报告尺寸，并且不会加载 native runtime。它用于输入准入和诊断，不代表文件一定完整有效，也不代表所有 codec 功能都可用。

## Identify First / 先识别

~~~csharp
ImageIdentifyResult identified = Cv2.Identify(encodedBytes);
if (identified.IsSizeKnown && (long)identified.Width * identified.Height > 100000000)
{
    throw new InvalidDataException("Image is larger than the application budget.");
}
~~~

ImageIdentifyResult distinguishes an unknown format, unknown dimensions, and a proven single-frame header. Classic TIFF (version 42, little- or big-endian) and BigTIFF (version 43 with 64-bit IFD offsets) report dimensions, page count, and cumulative pixels from a complete, bounded next-IFD chain when those facts are provable. When cumulative pixels, encoded depth, and channel count are all proven, `IsEstimatedPixelBytesKnown` is true and `EstimatedPixelBytes` records the checked encoded storage estimate. Heterogeneous page sizes keep the overall width/height fact unknown, but the parser can still prove `CumulativePixelCount` by summing every page when all page dimensions are known. Cyclic/out-of-range directories and incomplete directories keep the affected facts unknown; an unknown fact must not be treated as zero-sized input. BigTIFF facts are managed preflight facts and do not imply that the native codec is available.

ImageIdentifyResult 区分未知格式、未知尺寸和已证明的单帧头部。经典 TIFF（版本 42，支持小端/大端）和 BigTIFF（版本 43、64 位 IFD 偏移）会在事实可证明时，从完整且有界的 next-IFD 链报告尺寸、页数和累计像素。当累计像素、编码精度和通道数都已证明时，`IsEstimatedPixelBytesKnown` 为 true，`EstimatedPixelBytes` 报告经过 checked 算术得到的编码存储估算。页尺寸不一致时，整体宽高事实保持未知；但只要每一页的尺寸都已知，解析器仍可通过逐页求和证明 `CumulativePixelCount`。循环/越界目录或目录不完整时，受影响事实保持未知；未知事实不能被当作零尺寸输入。BigTIFF 事实属于托管层预检事实，并不代表 native codec 一定可用。

TIFF and BigTIFF share the same bounded directory walk. Duplicate ImageWidth, ImageLength, BitsPerSample, or SamplesPerPixel tags invalidate admission facts, including when the duplicate repeats the same value. Width/height require positive SHORT/LONG scalars (BigTIFF also permits LONG8); IFD/IFD8 pointers cannot supply dimensions. Explicit SamplesPerPixel requires one positive SHORT. BitsPerSample requires uniform SHORT values in `1..64`, either one scalar (the libtiff compatibility convention) or exactly one value per explicit sample; mismatched counts keep depth and storage facts unknown. Up to 65,535 explicit samples are supported. Absent tags remain unknown rather than inferring color, alpha, or sample-format defaults. Unordered unique tags remain readable; a SubIFD pointer is bounded data and is not followed as a page.

TIFF 与 BigTIFF 共用同一个有界目录遍历。ImageWidth、ImageLength、BitsPerSample 或 SamplesPerPixel 重复会使准入事实未知，即使重复值相同也如此。宽高要求正数 SHORT/LONG 标量（BigTIFF 额外允许 LONG8），IFD/IFD8 指针不能提供尺寸。显式 SamplesPerPixel 必须是单个正数 SHORT。BitsPerSample 要求 `1..64` 内一致的 SHORT 值，可以是一个标量（兼容 libtiff 的惯例），或恰好每个显式 sample 一个值；数量矛盾时深度和存储事实未知。支持最多 65,535 个显式 sample；缺失标签保持未知，不猜测颜色、alpha 或 sample-format 默认值。标签乱序但唯一时仍可读取；SubIFD 指针只作为有界数据，不递归计入页数。

The main chain still has a 65,536-directory cap and cycle detection. The total inspected directory entries cannot exceed input length divided by entry size, and sample-value scans have a separate input-length budget with one fixed successful-range cache for shared arrays. Exhausting the sample scan budget leaves depth/storage unknown while independently proven page and geometry facts can survive. Hostile declared counts never allocate matching arrays. These are directory/header facts: no exact EOF boundary, strip/tile completeness, compressed pixel validity, signedness/color conversion, native peak or cumulative allocation, or final Mat precision is claimed. Enable `RejectUnknownPixelFormat` when ambiguous sample descriptors must fail admission.

主目录链仍有 65,536 个目录上限及循环检测。总检查 entry 数不能超过输入长度除以 entry 大小；样本值扫描另设与输入长度相同的预算，使用一个固定的成功范围缓存处理共享数组。样本扫描预算耗尽时，深度/存储未知，独立证明的页数和 geometry 事实仍可保留。恶意声明数量不会触发对应数组分配。这些是目录/头部事实，不证明精确 EOF、strip/tile 完整性、压缩像素有效性、有符号属性/颜色转换、native 峰值或累计分配量，以及最终 Mat 精度。需要拒绝矛盾样本描述时应启用 `RejectUnknownPixelFormat`。

`TiffDirectoryPreflightTests` covers 42 actual test cases, including 12 regressions first demonstrated failing on the former implementation, both directory formats and byte orders, repeated admission tags, uniform/scalar sample layouts through 65,535 samples, huge counts/offsets, cycles, scan budgets, cumulative/storage overflow, and byte[]/Span/stream limits. Four embedded two-page RGB 4x3 files were encoded and decoded sample by sample with tifffile 2026.11.16: classic little/big-endian files are 452/520 bytes (8/16-bit), and BigTIFF little/big-endian files are 660/728 bytes (8/16-bit). Their exact hashes are recorded beside the fixtures; Pillow 13.0.0 independently confirms both 8-bit files. Structural prefixes and five-value byte mutation are covered, and the TIFF mutation test is mandatory in isolated process evidence.

`TiffDirectoryPreflightTests` 包含 42 个实际用例，其中 12 个回归先在旧实现上失败，覆盖两种目录格式与字节序、关键标签重复、最多 65,535 个 sample 的一致/标量位深、极大 count/offset、循环、扫描预算、累计/存储溢出和 byte[]/Span/stream 限制。四份嵌入的双页 RGB 4x3 文件由 tifffile 2026.11.16 编码、解码并逐样本比对：经典小端/大端为 452/520 字节（8/16 位），BigTIFF 小端/大端为 660/728 字节（8/16 位）。精确 hash 记录于 fixture 旁；Pillow 13.0.0 独立复核两份 8-bit 文件。测试覆盖结构前缀与五值逐字节 mutation，隔离进程证据必须实际通过 TIFF mutation 测试。

`Identify(Stream, ImageDecodeOptions)` applies the same admission policy while reading from the stream's current position. It reads no more than `MaxInputBytes + 1` bytes, restores the original position for seekable streams even when validation fails, and consumes non-seekable streams. This is deliberately a whole-input preflight rather than an incremental decoder: callers that need to preserve a non-seekable source must provide their own replayable buffering boundary.

`Identify(Stream, ImageDecodeOptions)` 会从流的当前位置读取并应用同一准入策略。它最多读取 `MaxInputBytes + 1` 字节；对于可 seek 流，即使验证失败也会恢复原位置；对于不可 seek 流则会消费输入。这是有意设计为完整输入预检，而非增量解码器：需要保留不可 seek 源的调用方必须自行提供可重放的缓冲边界。

For structurally complete GIF, APNG, and animated WebP containers, `FrameCount` is counted from the parsed frame/image records. APNG sequence numbers, declared frame count, WebP animation chunks, GIF image descriptors/extensions, and the final container terminator must all be consistent; truncation, trailing bytes, or an incomplete frame leave `IsFrameCountKnown` false. JPEG is treated as a known single frame only when a bounded marker walk proves a single supported SOF and an EOI marker at the exact input end. Static PNG/WebP/GIF inputs report one frame when their single-image boundary is proven. BMP reports one frame only for an exact, uncompressed BI_RGB payload whose checked row stride and pixel-data end match the file size; truncated, trailing, compressed, or arithmetic-overflow cases remain unknown.

对于结构完整的 GIF、APNG 和动画 WebP 容器，`FrameCount` 根据已解析的帧/图像记录统计。APNG 序列号与声明帧数、WebP 动画块、GIF 图像描述符/扩展块以及容器结束标记必须一致；截断、尾部多余字节或未完成帧都会使 `IsFrameCountKnown` 保持为 false。JPEG 只有在有界标记遍历证明单一受支持 SOF 且 EOI 精确位于输入末尾时才报告已知单帧。能够证明单图边界的静态 PNG/WebP/GIF 报告一帧。BMP 只有在输入长度精确匹配、压缩方式为 BI_RGB 且 checked 行 stride 与像素数据末尾都能对齐到文件大小时才报告单帧；截断、尾部字节、压缩输入或算术溢出保持未知。

APNG frame admission follows the [PNG specification's animation rules](https://www.w3.org/TR/png-3/#apng-frame-based-animation): a complete supported IHDR, one `acTL` before any IDAT, gap-free shared `fcTL`/`fdAT` sequences, positive frame dimensions within the canvas, and defined disposal/blend values. A control before IDAT includes the default image in the animation and must match the full canvas; a control after IDAT starts a separate animated frame, so the default still image is excluded from `FrameCount`. The IDAT run must be consecutive and contain data, later frames require their own fdAT data, and IDAT/fdAT cannot supply the same frame. Empty IDAT and four-byte sequence-only fdAT fragments are allowed within a frame whose combined data is nonempty. Frame counts require exact IEND completion and matching declarations. Cropped frames still use the complete canvas for cumulative-pixel and encoded-storage budgets. The parser keeps fixed state and allocates no frame table from declarations. These facts do not validate chunk CRCs, compressed pixel streams, expanded/native allocation, or final Mat precision; independent header and stored-metadata facts may remain known when animation facts fail.

APNG 帧准入遵循 [PNG 规范的动画规则](https://www.w3.org/TR/png-3/#apng-frame-based-animation)：完整且受支持的 IHDR、任何 IDAT 之前的单一 `acTL`、连续无重复的 `fcTL`/`fdAT` 共用序号、位于画布内的正数帧尺寸，以及已定义的 disposal/blend 值。IDAT 前的控制块将默认图像纳入动画，必须覆盖整个画布；IDAT 后的控制块开始独立动画帧，默认静态图不计入 `FrameCount`。IDAT 块必须连续且包含数据，后续帧需要各自的 fdAT 数据，不能用 IDAT/fdAT 混合供给同一帧。允许空 IDAT 和仅四字节序号的 fdAT 分片，但每帧合计数据必须非空。已知帧数还要求 IEND 精确闭合并与声明一致。裁剪帧的累计像素和编码存储预算仍按完整画布计算。解析只保存固定状态，不根据声明分配帧表。这些事实不验证块 CRC、压缩像素流、展开/native 分配量或最终 Mat 精度；动画事实失败时，独立的头部和 metadata 存储事实仍可能已知。

PNG header facts now require the complete 33-byte signature/IHDR boundary, a 13-byte IHDR, positive 31-bit dimensions, a standard color/depth pair, compression/filter method zero and interlace zero or one. A truncated or unsupported IHDR supplies neither dimensions nor pixels. A proven first header survives later truncation or contradictory chunks. Core completion additionally requires letter-only chunk names with an uppercase reserved third letter, recognized critical chunks, a unique initial IHDR, a nonempty consecutive IDAT run and empty IEND at exact EOF. Indexed images require one preceding PLTE with 1..256 RGB entries, no more than the bit depth permits; grayscale forbids PLTE, while RGB/RGBA may have an optional palette. PLTE and tRNS ordering, multiplicity and lengths must agree. These rules follow [PNG 3 chunk ordering](https://www.w3.org/TR/png-3/#5ChunkOrdering) and were cross-checked against the bundled libpng reader; upstream sources are unchanged.

PNG 头部事实现在要求完整的 33 字节签名/IHDR 边界、13 字节 IHDR、正数 31 位宽高、标准颜色/位深组合、值为零的压缩/过滤方法，以及零或一的交错方法。截断或不受支持的 IHDR 同时丢弃尺寸和像素事实；已证明的首个头部可在后续截断或矛盾 chunk 下保留。核心结构闭合还要求 chunk 名全部为字母且第三个保留字母大写、关键 chunk 已识别、首个 IHDR 唯一、IDAT 连续且合计负载非空，以及空 IEND 精确位于 EOF。索引图必须有先行且唯一的 PLTE，包含 1..256 个 RGB 条目且不超过位深可表示范围；灰度图禁止 PLTE，RGB/RGBA 可有可选色表。PLTE/tRNS 的顺序、数量和长度必须一致。规则依据 [PNG 3 chunk 顺序](https://www.w3.org/TR/png-3/#5ChunkOrdering)，并与仓库内 libpng reader 交叉核对；未修改上游源码。

Stored metadata/ICC lengths require the same core completion. iCCP is unique and precedes PLTE/IDAT; its name has 1..79 printable Latin-1 bytes without leading/trailing/repeated spaces, compression method is zero and stored compressed data is nonempty. Its name scan is capped at 80 bytes. eXIf is unique and precedes IDAT. MetadataBytes still sums whole tEXt/zTXt/iTXt/eXIf/iCCP payloads; IccProfileBytes counts only compressed iCCP profile bytes. PNG 3 permits sRGB alongside iCCP and masks unused high bits in tRNS samples; admission preserves both cases. The parser retains fixed state and skips bounded payloads without inflation or declared-length allocations. CRC values, compressed pixel/profile/text contents, Exif contents and other ancillary semantics remain unverified. APNG frame failures may still leave these independently proven stored lengths known.

metadata/ICC 存储长度要求同样的核心结构闭合。iCCP 必须唯一且位于 PLTE/IDAT 前，名称为 1..79 个可打印 Latin-1 字节，不允许首尾或连续空格，压缩方法为零且存储压缩负载非空；名称最多扫描 80 字节。eXIf 必须唯一且位于 IDAT 前。MetadataBytes 继续累计 tEXt/zTXt/iTXt/eXIf/iCCP 的整个负载，IccProfileBytes 只统计 iCCP 的压缩 profile 字节。PNG 3 允许 sRGB 与 iCCP 共存，并要求解码器屏蔽 tRNS 样本未使用的高位；准入保留这两种情况。解析器仅保存固定状态，跳过有界负载，不执行解压或按声明长度分配。CRC 值、像素/profile/文本压缩内容、Exif 内容及其他 ancillary 语义仍未验证。APNG 帧检查失败时，独立证明的这些存储长度仍可已知。

`PngHeaderPreflightTests` covers 108 actual cases, including 61 failures demonstrated on the former implementation, all standard color/depth pairs, palette/tRNS/ICC/Exif conflicts, strict policies, byte[]/Span/short-read streams, seek restoration, every strict prefix and five-value byte mutation. Fifteen embedded byte-authored 4x3 PNGs cover every standard color/depth pair, including three Adam7 images and a real 588-byte sRGB ICC with all three text chunk types. PyPNG 0.20220715.0 independently verified every original stored sample, including full 16-bit channels; Pillow 13.0.0 independently decoded every file and palette/tRNS expansion (multi-channel 16-bit output is exposed as 8-bit). Embedded lengths and SHA256 are fixed in tests and rechecked after insertion. The PNG mutation test must actually pass in isolated process evidence. Encoded channels remain IHDR channels, including one index channel for palette PNG; budgets round each encoded sample up to a byte and do not predict palette/alpha expansion, final Mat precision, native availability or peak/cumulative allocation.

`PngHeaderPreflightTests` 覆盖 108 个实际用例，其中 61 个先在旧实现上失败；覆盖全部标准颜色/位深组合、调色板/tRNS/ICC/Exif 矛盾、严格策略、byte[]/Span/短读流、seek 恢复、每个严格前缀和五值逐字节 mutation。嵌入的 15 份手工编码 4x3 PNG 覆盖全部标准颜色/位深组合，其中 3 份为 Adam7，一份包含真实的 588 字节 sRGB ICC 和三种文本 chunk。PyPNG 0.20220715.0 独立核对全部原始存储样本，包括完整 16 位多通道值；Pillow 13.0.0 独立解码全部文件及调色板/tRNS 展开（多通道 16 位输出以 8 位暴露）。测试固定嵌入文件的长度和 SHA256，并在插入后重新核对。PNG mutation 必须在隔离进程证据中实际通过。编码通道始终取自 IHDR，调色板 PNG 为一个索引通道；预算将每个编码样本向上取整到字节，不推断色表/alpha 展开、最终 Mat 精度、native 可用性或峰值/累计分配量。

## Decode With A Budget / 带预算解码

~~~csharp
var options = new ImageDecodeOptions(
    maxInputBytes: 64L * 1024 * 1024,
    maxWidth: 16384,
    maxHeight: 16384,
    maxPixels: 100000000,
    maxFrames: 64,
    rejectUnknownFormat: true,
    requireKnownSize: true,
    maxMetadataBytes: 8L * 1024 * 1024,
    maxIccProfileBytes: 2L * 1024 * 1024,
    requireKnownMetadataSize: true,
    requireKnownIccProfileSize: true);

using (Mat image = Cv2.ImDecode(encodedBytes, options, ImreadModes.Color))
{
    // Native decoding starts only after the managed budget checks pass.
}
~~~

The same policy is available for a stream. Its seek/consumption behavior is identical to `Identify(Stream, ImageDecodeOptions)`.

对于流也可以使用同一策略，其 seek/消费语义与 `Identify(Stream, ImageDecodeOptions)` 完全相同。

~~~csharp
using (Mat image = Cv2.ImDecode(uploadStream, options, ImreadModes.Color))
{
    // A seekable uploadStream remains at its original position after this call.
}
~~~

The overload checks encoded byte length, recognized format, known dimensions, checked width-times-height arithmetic, known frame/page count, cumulative width-times-height budget, encoded depth/channel limits when proven, an optional `MaxEstimatedPixelBytes` budget, and known metadata/ICC payload limits before calling the existing native ImDecode. The byte estimate uses proven cumulative pixels multiplied by encoded sample storage and channel count; it is an admission estimate, not a native peak allocation guarantee. The original overloads remain unchanged for applications that already enforce their own input policy. A preflight pass does not replace sandboxing, codec patching, timeout controls, or post-decode validation.

该重载会在调用现有 native ImDecode 前检查编码字节长度、可识别格式、已知尺寸、checked 的宽高乘法、累计宽高像素预算、已证明的编码精度/通道上限、可选的 `MaxEstimatedPixelBytes` 预算以及已知 metadata/ICC 负载上限。字节估算使用已证明的累计像素数乘以编码样本存储宽度和通道数；它是输入准入估算，不是 native 峰值分配保证。原有重载保持不变，已经有自有输入策略的应用可以继续使用。预检不能替代沙箱、codec 更新、超时控制或解码后的结果校验。

## Metadata And ICC Facts / Metadata 与 ICC 事实

For structurally complete PNG, JPEG, GIF, and WebP containers, `ImageIdentifyResult` reports `MetadataBytes` and `IccProfileBytes` when the managed parser can prove their serialized payload lengths. The selected metadata count includes PNG `tEXt`/`zTXt`/`iTXt`/`eXIf`/`iCCP`, JPEG APPn and COM segments, GIF extension payloads, and WebP EXIF/XMP/ICCP chunks. It is a stored-byte admission fact, not an estimate of expanded EXIF, XMP, compressed PNG `iCCP`, or native decoder allocation. For other formats, truncated containers, or unsupported container details, the corresponding fact is unknown.

对于结构完整的 PNG、JPEG、GIF 和 WebP 容器，若 managed 解析器能够证明序列化负载长度，`ImageIdentifyResult` 会报告 `MetadataBytes` 和 `IccProfileBytes`。选定的 metadata 统计包括 PNG 的 `tEXt`/`zTXt`/`iTXt`/`eXIf`/`iCCP`、JPEG APPn/COM 段、GIF 扩展块负载，以及 WebP EXIF/XMP/ICCP 块。该数值是存储字节的准入事实，不是展开后的 EXIF、XMP、压缩 PNG `iCCP` 或 native 解码分配量的估算。对于其他格式、截断容器或尚未支持的容器细节，相应事实为未知。

JPEG uses one bounded marker walk for SOF/SOS component tables, scan escapes/restart markers, APPn/COM payloads, and the exact EOI boundary. A zero-height non-hierarchical SOF may resolve its height only through one length-four DNL marker encountered inside entropy data; DNL outside a scan, duplicate DNL, zero height, or a non-zero-height SOF with DNL keeps the affected facts unknown. Metadata includes ICC fragment headers but excludes segment markers and length fields. ICC data requires the exact `ICC_PROFILE\0` signature and one complete set of 1–255 uniquely numbered fragments with a consistent count; physical ordering is unrestricted. A missing, duplicate, zero-indexed, inconsistent, or truncated ICC fragment leaves both metadata facts unknown while preserving a separately proven frame boundary. No ICC buffer is assembled. Segment truncation, missing EOI, or trailing bytes leave frame/metadata facts unknown, while an earlier proven SOF can retain dimensions and encoded pixel facts. Multiple SOFs and hierarchical/differential frames remain unsupported. Marker completion does not validate entropy coding, ICC content, native decodability, or final Mat precision; the existing SOF-without-SOS structural boundary remains admissible.

 JPEG 使用同一次有界标记遍历检查 SOF/SOS 组件表、扫描转义/restart 标记、APPn/COM 负载和精确 EOI 尾界。非层次 SOF 的高度为零时，只有在熵数据中遇到一个长度为 4 的 DNL 标记才能解析高度；扫描外 DNL、重复 DNL、零高度或已有非零 SOF 高度再出现 DNL，均使相关事实保持未知。Metadata 包含 ICC 分片头，但不计段标记和长度字段。ICC 数据要求精确的 `ICC_PROFILE\0` 签名，以及数量一致、序号唯一且完整的 1–255 个分片；物理存放顺序不限。缺失、重复、零序号、数量不一致或截短的 ICC 分片会使两项 metadata 事实保持未知，但保留独立证明的帧边界；不拼接 ICC 缓冲区。段截断、缺失 EOI 或尾部多余字节使帧和 metadata 事实未知，先前已证明的 SOF 尺寸及编码像素事实仍可保留。多 SOF 与 hierarchical/differential frame 仍不支持。标记闭合不验证熵编码、ICC 内容、native 可解码性或最终 Mat 精度；保留现有 SOF 后直接 EOI、无 SOS 的结构边界语义。

GIF counts every extension payload: comment and unknown-label data sub-blocks, the four-byte graphics-control payload, application identifiers/authentication codes plus their data, and plain-text headers plus text data. Introducers, labels, size bytes, terminators, palettes, and image data are excluded. `IccProfileBytes` sums only the data sub-block payloads of applications with the exact `ICCRGBG1012` identifier/authentication code, including repeated applications; no profile buffer is assembled or expanded. These counts require a GIF87a/GIF89a header, at least one image record, and an exact final trailer. A malformed fixed block, incomplete sub-block, missing trailer, or trailing input discards both metadata facts. A complete container without extensions reports known zero lengths. These are serialized-byte facts and do not validate ICC content or LZW pixels.

GIF 统计所有扩展块负载：comment 和未知 label 的 data sub-block、四字节 graphics-control 负载、application 标识/认证码及其数据，以及 plain-text 头和文本数据。不计 introducer、label、长度字节、terminator、色表或图像数据。`IccProfileBytes` 仅累计标识/认证码精确为 `ICCRGBG1012` 的 application data sub-block 负载，重复 application 也累计；不拼接或展开 profile 缓冲区。只有 GIF87a/GIF89a 头、至少一个 image record 和精确的末尾 trailer 均成立时，才报告这些长度。固定块损坏、sub-block 不完整、缺失 trailer 或尾部多余输入都会丢弃两项 metadata 事实。完整且没有扩展块的容器报告已知零长度。这些是序列化字节事实，不验证 ICC 内容或 LZW 像素。

`MaxMetadataBytes` and `MaxIccProfileBytes` reject only known facts. Set `RequireKnownMetadataSize` and `RequireKnownIccProfileSize` for a fail-closed boundary; otherwise an unknown metadata fact remains admissible, like an unknown image size when `RequireKnownSize` is disabled.

`MaxMetadataBytes` 和 `MaxIccProfileBytes` 只拒绝已知事实。设置 `RequireKnownMetadataSize` 和 `RequireKnownIccProfileSize` 可形成失败关闭边界；否则未知 metadata 事实仍会被允许，这与未启用 `RequireKnownSize` 时的未知图像尺寸一致。

## Policy Boundaries / 策略边界

- ImageDecodeOptions is an admission budget, not a promise of peak native allocation.
- Stream preflight buffers the complete admitted input in managed memory; MaxInputBytes limits that buffer but does not bound native peak allocation.
- Unknown dimensions or frame counts are accepted by default unless RequireKnownSize is enabled; applications handling untrusted input should choose an explicit policy.
- A recognized signature can still be truncated, malformed, or hostile. Native failure remains possible and must be handled.
- Other format-specific multi-frame parsers, native peak-allocation accounting, decoded color/final precision facts, and IBufferWriter output remain separate follow-up contracts. Classic TIFF and BigTIFF cumulative accounting is available only when every inspected page dimension is proven.

- ImageDecodeOptions 是输入准入预算，不是 native 峰值内存承诺。
- 流预检会将已准入的完整输入缓冲到 managed 内存中；MaxInputBytes 限制该缓冲，但不限制 native 峰值分配。
- 默认允许未知尺寸或帧数；处理不可信输入时应显式设置策略，例如启用 RequireKnownSize。
- 已识别的签名仍可能被截断、损坏或恶意构造，native 失败仍然可能发生，调用方必须处理。
- 其他格式专用多帧解析器、native 峰值分配核算、解码后颜色/最终精度事实和 IBufferWriter 输出仍属于后续独立契约。经典 TIFF 与 BigTIFF 的累计核算仅在每个已检查页面尺寸均可证明时生效。
## Pixel Format And Multi-Frame Budgets / 像素格式与多帧预算

For PNG, the parser reports `BitDepth` and channel count from a valid IHDR color type. For JPEG, it reports sample precision and component count from a complete, single non-hierarchical SOF component table. Raw J2K and bounded JP2 codestream boxes report dimensions, component count, and a uniform component precision from a complete SIZ marker; mixed component precision keeps `BitDepth` unknown because the public result has no per-component representation. The JPEG 2000 SIZ fact does not prove a complete codestream or native support for its signedness, precision, component count, color space, or subsampling, so frame and cumulative-pixel facts remain unknown. WebP reports 8-bit RGB/RGBA only after bounded container and VP8/VP8L headers prove the frame layout; VP8X/ALPH/VP8L alpha information determines the channel budget. BMP reports 1/4/8-bit indexed storage and 8-bit BGR storage for 24/32-bit uncompressed BI_RGB headers; compressed, bitfield, and unknown DIB layouts remain unknown. GIF reports indexed channel storage and the color-table bit width only when the signature is exactly GIF87a or GIF89a and every complete frame has the same proven global or local color-table depth; invalid versions or inconsistent frame depths keep pixel-format facts unknown. Sun Raster reports 1/8-bit single-channel, 8-bit BGR, or 8-bit four-byte storage for a complete supported header and payload range. Radiance HDR reports 8-bit, four-component RGBE/XYZE storage after one supported FORMAT and complete signed-axis geometry; the shared exponent is not alpha, and final OpenCV `Mat` depth is determined separately by the read mode. Single-frame and cumulative-pixel facts require exact per-record flat, old-repeat or component-RLE boundaries. OpenEXR reports `dataWindow` dimensions from a complete first header and reports channel count plus a uniform 16- or 32-bit channel storage depth when the `channels` attribute is complete; mixed channel storage keeps depth unknown. OpenEXR `HALF` is decoded by OpenCV to 32-bit float, so these remain encoded-header facts, not final `Mat` depth or a proof of payload/frame completeness. Classic TIFF and BigTIFF report a uniform `BitsPerSample` value and `SamplesPerPixel` value when every inspected page proves the same values. PNM P1/P4 reports its one-bit monochrome header, P2/P5 and P3/P6 report one or three channels and 8- or 16-bit storage implied by `maxval`; PAM P7 reports 8- or 16-bit storage and arbitrary positive DEPTH channels after a complete `ENDHDR`, while PF/Pf reports 32-bit float RGB or grayscale after a valid non-zero scale token. These are encoded-header facts; they do not promise the final `Mat` depth or channel layout after `ImreadModes` conversion. Other formats remain unknown until their headers can be proven without guessing.

对于 PNG，解析器从合法 IHDR 色彩类型报告 `BitDepth` 和通道数；对于 JPEG，解析器从完整、单一的非层次 SOF 组件表报告样本精度和组件数。原始 J2K 与边界完整的 JP2 codestream box 会从完整 SIZ 标记报告尺寸、组件数及统一的组件精度；组件精度不一致时 `BitDepth` 保持未知，因为当前公开结果没有逐组件表达能力。JPEG 2000 的 SIZ 事实不证明 codestream 完整，也不证明 native 支持其有符号属性、精度、组件数、色彩空间或子采样，因此帧数与累计像素保持未知。WebP 仅在有界容器及 VP8/VP8L 头证明帧布局后报告 8-bit RGB/RGBA，通道预算由 VP8X/ALPH/VP8L alpha 信息确定。BMP 对未压缩 BI_RGB 头报告 1/4/8-bit 索引存储，或 24/32-bit 输入对应的 8-bit BGR 存储；压缩、bitfield 及未知 DIB 布局保持未知。GIF 仅当签名精确为 GIF87a 或 GIF89a，且每个完整帧都能证明一致的全局或局部颜色表位宽时，才报告索引通道存储和颜色表位宽；错误版本或帧位宽不一致时保持像素格式事实未知。Sun Raster 在受支持的头部和 payload 范围完整时报告 1/8-bit 单通道、8-bit BGR 或 8-bit 四字节存储。Radiance HDR 在唯一受支持 FORMAT 和完整有符号轴 geometry 后报告 8-bit、四分量 RGBE/XYZE 存储；共享指数不是 alpha，最终 OpenCV `Mat` 深度仍由读取模式另行决定。只有逐 record 的 flat、旧式重复或 component-RLE 边界能够被精确证明时，才报告已知单帧和累计像素。OpenEXR 在首个 header 完整且 `dataWindow` 合法时报告尺寸；当 `channels` 属性完整且所有通道统一为 16 或 32-bit 时报告通道数和存储深度，混合通道深度则只保留通道数事实。OpenEXR 的 `HALF` 在 OpenCV 中解码为 32-bit float，因此这些仍是编码头事实，不是最终 `Mat` 深度，也不证明 payload/帧完整。经典 TIFF 和 BigTIFF 在每个已检查页面都能证明相同值时报告统一的 `BitsPerSample` 和 `SamplesPerPixel`。PNM 的 P1/P4 报告头部规定的单通道 1-bit；P2/P5 与 P3/P6 报告一个或三个通道，以及由 `maxval` 推导出的 8/16-bit 存储宽度；PAM P7 在完整 `ENDHDR` 后报告 8/16-bit 存储和由正数 DEPTH 指定的任意通道数，PF/Pf 在 scale 非零且语法有效时报告 32-bit float RGB 或灰度。这些是编码头事实，不承诺 `ImreadModes` 转换后的最终 `Mat` 深度或通道布局。其他格式只有在无需猜测且头部可证明时才会报告，否则保持未知。

BMP dimensions require a complete established DIB layout (12/40/52/56/64/108/124 bytes), one color plane and a recognized bit count. CORE reads unsigned 16-bit width/height; OS/2 2.x reads unsigned 32-bit dimensions; Windows uses signed height for top-down images, excluding `Int32.MinValue`. Unknown or truncated DIB layouts do not borrow geometry from INFO offsets. For known layouts, proven geometry survives unavailable pixel/storage facts. Uncompressed BI_RGB frame/storage facts additionally require zero file-header reserved words, exact declared file size, a complete required color table before pixels, and zero or exact `biSizeImage`. Indexed 1/4/8-bit palettes use three-byte CORE entries or four-byte entries; zero color count means the full palette, while explicit counts must fit the bit depth. Optional true-color tables and gap bytes are range-checked without interpreting pixels. Checked four-byte row alignment and pixel end must fit the actual input. No allocations use declared DIB, color-table, image or profile lengths.

BMP 尺寸要求完整的已知 DIB 布局（12/40/52/56/64/108/124 字节）、一个颜色平面及已识别的 bit count。CORE 使用无符号 16 位宽高，OS/2 2.x 使用无符号 32 位宽高，Windows 的有符号高度允许顶向下图像，但不接受 `Int32.MinValue`。未知或截断的 DIB 不借用 INFO 偏移猜测尺寸；已知布局中，像素/存储事实不可证明时仍保留已证明的尺寸。未压缩 BI_RGB 的帧/存储事实还要求文件头保留字为零、声明文件长度精确、像素前的必需色表完整，以及 `biSizeImage` 为零或精确值。1/4/8 位索引色表使用 CORE 三字节或其他布局四字节条目；颜色数为零表示完整色表，显式颜色数不得超出位深。可选真彩色表及间隙字节只检查范围，不解释像素；checked 的四字节行对齐和像素尾界受真实输入限制。不按声明的 DIB、色表、图像或 profile 长度分配。

For V5 `PROFILE_EMBEDDED`/`PROFILE_LINKED`, the positive profile byte range must follow the pixels and end exactly at file EOF; its offset is relative to the DIB start. Linked names are never opened, and inactive profile pointers for other color spaces are ignored. This proves a stored range, not ICC validity, preservation or color conversion, so BMP metadata/ICC lengths remain unknown. BI_RGB 16-bit packed 5/5/5 can prove its exact frame range, but its nonuniform component layout remains unknown in the uniform-depth API. Compressed and bitfield pixel/frame facts remain unknown. The shared pixel estimate rounds each encoded sample to a byte; it excludes palette expansion, BGRX padding, row padding and profile bytes and is not native peak allocation. See the [CORE](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-bitmapcoreheader), [INFO](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-bitmapinfoheader), [V5](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-bitmapv5header) and [bitmap storage](https://learn.microsoft.com/en-us/windows/win32/gdi/bitmap-storage) specifications. OpenCV 5.0.0 `grfmt_bmp.cpp` was independently reviewed; source layouts do not imply native decoder support or final Mat precision.

V5 的 `PROFILE_EMBEDDED`/`PROFILE_LINKED` 正长度 profile 必须位于像素之后且精确结束于文件 EOF，偏移相对于 DIB 起点。绝不打开 linked 名称；其他色彩空间的非活动 profile 指针被忽略。这只证明存储范围，不证明 ICC 有效、保留或颜色转换，BMP metadata/ICC 长度仍未知。BI_RGB 16 位打包 5/5/5 可以证明精确帧范围，但统一位深 API 无法表达其分量布局；压缩和 bitfield 的像素/帧事实仍未知。共享像素估算将每个编码样本向上取整到字节，排除色表展开、BGRX 额外字节、行填充和 profile，不等于 native 峰值分配。独立核对格式文档及 OpenCV 5.0.0 的 `grfmt_bmp.cpp`，未修改上游源码；格式布局不等于 native 可解码或最终 Mat 精度。

`BmpHeaderPreflightTests` 有 77 个实际用例，其中 19 个回归先在旧实现上失败；覆盖七种 DIB、索引色表、Windows 顶向下尺寸、CORE 尺寸极值、声明/范围冲突、profile 指针、未知事实严格策略、byte[]/Span/短读流及 seek 恢复、严格前缀和五值 mutation。十份嵌入的 4x3 BMP 由 Pillow 13.0.0 逐样本独立解码：INFO RGB24/index8/mono1（90/1090/74 字节）、CORE RGB24/index4（62/86）、顶向下 BGRX32（102）、V4 RGB24（158）、带 588 字节 sRGB profile 的 V5 RGB24（762）、V5 BGRA32 bitfields（186）及 OS/2 RGB24（114）。INFO 文件由 Pillow 编码，其他布局以显式格式字节构造并由其解码。测试固定长度/SHA256，嵌入后再次复核全部解码样本，包括色表展开与 alpha。BMP mutation 必须在隔离进程证据中实际通过。这些检查不验证像素索引值、ICC 内容、native 可用性、调色板/颜色转换或 native 峰值/累计分配。

OpenEXR admission inspects one complete first header for versions 1/2 with known tiled, long-name, deep and multipart flags. `dataWindow` must be one correctly typed `box2i`; `channels`, when present, must be one correctly typed `chlist`. Duplicate admission attributes or duplicate byte-exact channel names discard geometry and pixel facts together, including wrong-typed duplicates in either order. Missing channels retain proven geometry with unknown pixel facts. Names are bounded to 255 actual terminated bytes, and channels to 65,535 actual records; no storage is allocated from a declared attribute size. Channel names preserve distinct raw bytes, including invalid UTF-8. Positive sampling must divide the data-window origin and dimensions; a known tiled/deep first part requires unit sampling. The multipart file-wide deep flag does not impose a later deep part's rules on an ordinary first part. UINT/FLOAT storage is 32 bits and HALF is 16; mixed widths retain channel count with unknown depth. `pLinear` and reserved channel bytes do not change these facts. The source reference is external [OpenEXR 3.5.4](https://github.com/AcademySoftwareFoundation/openexr/tree/v3.5.4/src/lib/OpenEXR), including `ImfHeader.cpp`, `ImfChannelListAttribute.cpp`, `ImfChannelList.cpp`, `ImfName.h` and `ImfVersion.h`; OpenCV 5 discovers OpenEXR 3 externally. No upstream source is changed.

OpenEXR 准入检查版本 1/2、已知 tiled/long-name/deep/multipart 标志和完整的首个头部。`dataWindow` 必须为唯一且类型正确的 `box2i`；存在 `channels` 时必须为唯一且类型正确的 `chlist`。重复准入属性或逐字节相同的通道名会一起丢弃尺寸和像素事实，包括前后任意顺序的错误类型重复属性。缺少 channels 时保留已证明的尺寸，像素事实未知。名称最多为实际读取且零终止的 255 字节，通道最多为实际读取的 65,535 条记录；不按声明的属性长度分配存储。通道名保留不同原始字节，包括无效 UTF-8。正采样因子须整除 dataWindow 原点和宽高；已知 tiled/deep 首部件要求单位采样。multipart 文件级 deep 标志不会把后续 deep 部件的规则套用到普通首部件。UINT/FLOAT 存储为 32 位、HALF 为 16 位；混合位宽保留通道数而深度未知。`pLinear` 和通道保留字节不影响这些事实。独立源核对使用外部 OpenEXR 3.5.4 的头、通道表、名称及版本实现；OpenCV 5 通过外部依赖发现 OpenEXR 3，未修改上游源码。

Header facts do not prove chunks/pixels, exact EOF, frame count, aggregate storage, peak/cumulative native allocation, native decoder availability or final Mat precision.

`OpenExrHeaderPreflightTests` 有 51 个实际用例，其中 12 个回归先在旧实现上失败；覆盖属性顺序/类型、通道名及采样、尺寸/名称/通道数边界、未知事实严格策略、byte[]/Span/短读流、seek 恢复、首个头部终止前的全部前缀，以及五值逐字节 mutation。OpenEXR 3.5.4 / NumPy 2.3.5 生成七份文件并逐样本独立解码：HALF RGB（413 字节）、负原点 FLOAT RGBA（600）、UINT Z（402）、混合 HALF/FLOAT（444）、tiled（450）、第二部件尺寸不同的 multipart（901），以及每像素两个样本的 deep scanline（600）。首部件均为 4x3，测试固定长度及 SHA256，嵌入后再次复核所有部件的解码样本。OpenEXR mutation 必须在隔离进程证据中实际通过。头部事实不证明 chunk/像素、精确 EOF、帧数、汇总存储、native 峰值/累计分配、native decoder 可用性或最终 Mat 精度。

JPEG 2000 SIZ inspection checks the Part 1 limits of 1–38 encoded bits per component, 1–16,384 components, non-zero subsampling factors, valid image/tile origins, and at most 65,535 tiles. Tile ceil division uses widened arithmetic for reference-grid coordinates near `2^32`. Uniform precision is reported even when sign descriptors differ in a raw stream; mixed precision keeps depth unknown. These are format facts: the bundled OpenJPEG reader supports at most 31 bits, and a reported 32–38-bit header does not claim native decoding support.

JPEG 2000 的 SIZ 检查包括 Part 1 的每组件 1–38 位编码精度、1–16,384 个组件、非零子采样因子、合法图像/tile 原点及最多 65,535 个 tile。tile 向上取整使用加宽算术，支持接近 `2^32` 的参考网格坐标。裸码流的符号描述可以不同；位深一致时仍报告统一精度，混合精度保持未知。这些属于格式事实：所捆绑的 OpenJPEG reader 最多支持 31 位，识别出 32–38 位头部不表示 native 可解码。

JP2 facts additionally require the signature, an immediately following JP2-compatible `ftyp`, exactly one `jp2h` before exactly one `jp2c`, and bounded top-level boxes through file EOF. The first `jp2h` child must be a unique 14-byte `ihdr`; width, height, component count and all sign/precision descriptors must agree with SIZ. `BPC=255` requires one unique `bpcc` containing exactly one descriptor per component. A redundant BPCC with constant BPC is accepted only when both representations agree with SIZ. Short, extended 64-bit and to-EOF box lengths are bounded by the actual input and parent range; to-EOF lengths refer to file EOF, including within a superbox. Unknown boxes remain opaque and are not recursively searched for header facts. Duplicate required boxes, conflicting descriptors, broken parent/child boundaries and malformed suffixes discard dimensions and encoded pixel facts together. The walks use constant parser state and do not allocate by declared component/box lengths.

JP2 事实还要求完整签名、紧随其后的 JP2-compatible `ftyp`、恰好一个先于唯一 `jp2c` 的 `jp2h`，以及直到文件 EOF 均有界的顶层盒。`jp2h` 首个子盒必须是唯一且负载为 14 字节的 `ihdr`，宽高、组件数及全部符号/精度描述必须与 SIZ 一致。`BPC=255` 要求唯一 `bpcc`，且恰好每组件一个描述；常量 BPC 的冗余 BPCC 仅在两者均与 SIZ 一致时接受。普通长度、64 位扩展长度和到 EOF 的长度受实际输入及父范围约束；即使在 superbox 内，到 EOF 的长度仍指文件 EOF。未知盒作为不透明数据跳过，不递归寻找头部事实。必需盒重复、描述矛盾、父子越界或损坏尾盒使尺寸与编码像素事实一起未知。遍历只使用固定解析状态，不按声明的组件数或盒长度分配数组。

Length and SHA256 are fixed by actual tests, with decoded sample hashes independently rechecked after embedding. The JPEG 2000 mutation test is mandatory for isolated process evidence. `Jpeg2000HeaderPreflightTests` 有 52 个实际用例，其中 12 个回归先在旧实现上失败；覆盖有符号/一致/混合描述、组件和 tile 极值、普通/扩展/到 EOF 的盒、重复及矛盾头部、严格前缀及五值逐字节 mutation，还有 byte[]/Span/短读流限制及 seek 恢复。Pillow 13.0.0 / OpenJPEG 2.5.4 生成五份无损 4x3 文件并逐样本解码比对：RGB JP2/J2K 为 292/207 字节，RGBA JP2 为 353 字节，16 位灰度 JP2/J2K 为 229/144 字节。实际测试固定长度与 SHA256，嵌入后再次独立复核解码样本 hash。隔离进程证据必须实际通过 JPEG 2000 mutation 测试。这些头部仍不证明帧数、累计像素、编码像素存储估算、压缩数据有效性、调色板/颜色展开、native 分配量或最终 Mat 精度。

WebP reads simple lossy VP8 dimensions at their actual bitstream offsets and also supports simple VP8L dimensions. Frame and encoded pixel facts share one bounded container walk: the RIFF length and zero padding must be exact, VP8X must be first when present, canvas area must be at most `2^32 - 1`, and static and animated image data cannot mix. Each ANMF requires a rectangle inside the canvas (its stored offsets are doubled), one complete bounded VP8/VP8L header matching that rectangle, and data beyond the header. Optional ALPH must precede lossy VP8, use supported compression/preprocessing, and have the exact raw sample length when uncompressed. Nested chunks cannot cross ANMF boundaries; duplicate image/alpha chunks and misplaced reconstruction chunks keep frame/pixel facts unknown. Unknown chunks after a frame's image are skipped without recursion. Reserved fields and future VP8X fields are ignored as required by the [WebP container specification](https://developers.google.com/speed/webp/docs/riff_container).

WebP 从真实的 bitstream 偏移读取普通有损 VP8 尺寸，并支持普通 VP8L 尺寸。帧数和编码像素事实共用一次有界容器遍历：RIFF 长度与零填充必须精确，存在 VP8X 时它必须为首块，画布面积最多为 `2^32 - 1`，且静态/动画图像数据不能混用。每个 ANMF 都要求矩形位于画布内（存储的偏移需乘二），存在且仅存在一个与矩形尺寸一致的完整有界 VP8/VP8L 头，并有头部之后的数据。可选 ALPH 必须在有损 VP8 前，使用受支持的压缩/预处理值；未压缩时样本长度须精确。嵌套块不能越过 ANMF 边界，重复图像/alpha 块或重建块错序会使帧和像素事实未知。帧图像之后的未知块只跳过、不递归；按 [WebP 容器规范](https://developers.google.com/speed/webp/docs/riff_container) 忽略保留字段及未来 VP8X 字段。

Cropped WebP frames budget the full canvas for every frame. The VP8X alpha flag budgets four channels across the animation even when some frames are opaque; VP8L's alpha field remains a header hint. A header-only ANMF no longer supplies frame or pixel facts. Earlier proven dimensions and separately counted stored metadata may remain known, so callers requiring complete pixel facts should use `RejectUnknownPixelFormat`. These checks do not validate compressed pixels, ICC contents, native decodability or peak/cumulative native allocation, or final Mat precision.

WebP 裁剪帧的每帧预算仍按整个画布计算。VP8X alpha 标志为整段动画按四通道预算，即使部分帧不透明；VP8L alpha 字段仍属于头部提示。只有帧头的 ANMF 不再提供帧数或像素事实。已证明的尺寸和独立统计的存储 metadata 可保留已知，要求完整像素事实的调用方应启用 `RejectUnknownPixelFormat`。这些检查不验证压缩像素、ICC 内容、native 可解码性、native 峰值/累计分配量或最终 Mat 精度。

AVIF size and pixel facts come only from properties associated with the primary item: `meta/pitm` identifies the item, and `iprp/ipma` resolves its one-based `ipco` indices. An associated `ispe` proves encoded dimensions; an associated uniform 8/10/12-bit `pixi` with 1, 3, or 4 channels additionally proves encoded pixel facts. Thumbnail and unassociated properties are excluded. Missing associations keep size and pixel facts unknown; absent or unsupported primary `pixi` keeps pixel facts unknown while preserving proven dimensions. This corrects the earlier behavior that combined every `ispe/pixi` in the property container. Callers using `RequireKnownSize` or `RejectUnknownPixelFormat` now reject inputs whose primary facts cannot be proven.

AVIF 的尺寸和像素事实仅来自主图关联的属性：`meta/pitm` 指定 item，`iprp/ipma` 将其从 1 开始的属性索引解析到 `ipco`。关联的 `ispe` 证明编码尺寸；关联的统一 8/10/12-bit `pixi` 且通道数为 1、3 或 4 时，额外证明编码像素事实。缩略图和未关联属性不参与统计；缺失关联时尺寸和像素事实保持未知，主图 `pixi` 缺失或不受支持时只保留已证明的尺寸。这修正了先前汇总整个属性容器中所有 `ispe/pixi` 的行为；启用 `RequireKnownSize` 或 `RejectUnknownPixelFormat` 的调用方现在会拒绝无法证明主图事实的输入。

The parser supports `pitm`/`ipma` versions 0 and 1, 16/32-bit item IDs, 7/15-bit property indices, and all four supported `ipma` version/flag pairs. It rejects duplicate or unordered item IDs, repeated version/flag pairs, invalid essential-zero indices, out-of-range associations, duplicate primary properties, unsupported full-box versions/flags, and truncated or trailing box bytes. Four fixed cursors merge the association tables; a fixed 255-entry array holds the primary item's associations, so a declared entry count cannot request proportional storage. Ordinary and extended box lengths are bounded by their parent. The `ftyp` signature reads brands only inside its declared payload. These remain encoded-header facts: item extents, AV1 payload, transformations, frame count, cumulative allocation, and final `Mat` precision are not proven. A header ending exactly after `meta` can prove dimensions while payload completeness remains unknown. Rollback must preserve unknown facts instead of restoring unrelated-property aggregation.

解析器支持 `pitm`/`ipma` 的版本 0/1、16/32 位 item ID、7/15 位属性索引和四种受支持的 `ipma` 版本/flags 组合。重复或乱序 item ID、重复版本/flags、带 essential 标志的零索引、越界关联、重复主图属性、不受支持的 full-box 版本/flags，以及 box 截断或尾部多余字节均会使相关事实未知。四个固定 cursor 合并关联表，固定 255 项数组保存主图关联，不按声明 entry count 分配对应大小的存储。普通和扩展 box 长度均受父范围约束，`ftyp` 签名只在其声明负载中读取品牌。这些仍是编码头事实，不证明 item extent、AV1 payload、变换、帧数、累计分配或最终 `Mat` 精度；恰好结束于 `meta` 的头部可证明尺寸，但 payload 完整性仍未知。回滚应保留未知事实，不能恢复将无关属性汇总为主图的行为。

PFM `PF`/`Pf` headers prove three/one encoded channels, positive dimensions and IEEE float32 storage only after a complete nonzero decimal scale token. The fixed-state scanner accepts an optional sign, decimal point and scientific exponent without allocating a token string or converting to `double`. A nonzero coefficient remains valid header syntax even for `1e309`, `1e-400` or longer exponents; a zero coefficient, NaN, Infinity and malformed syntax do not prove header facts. This follows the [Netpbm PFM description](https://netpbm.sourceforge.net/doc/pfm.html); native scale representability and conversion are separate.

PFM 的 `PF`/`Pf` 头部只有在完整非零十进制 scale token 后，才证明三/单通道、正数尺寸和 IEEE float32 编码存储。固定状态扫描器支持可选符号、小数点和科学计数指数，不分配 token 字符串，也不转换为 `double`。即使是 `1e309`、`1e-400` 或更长指数，只要系数非零仍属合法头部语法；零系数、NaN、Infinity 和错误语法不证明头部事实。规则参考 [Netpbm PFM 描述](https://netpbm.sourceforge.net/doc/pfm.html)；native scale 的表示范围和转换独立处理。

Exactly one whitespace byte terminates scale. After a CR delimiter, LF is the first raster byte; additional whitespace or `#` bytes are never skipped as header content. Existing PNM-style comments before fields or immediately attached to scale remain a compatibility extension, terminated by CR or LF; they are not a standard PFM feature. Only checked `width * height * channels * 4` arithmetic and an exact raster ending at the input end prove single-frame, cumulative-pixel and encoded-storage facts. Truncation, extra bytes, concatenated images or arithmetic overflow keep completion unknown while preserving a proven header. Metadata/ICC lengths, float sample validity, orientation/color semantics, native allocations and final `Mat` precision remain unknown. OpenCV's native PFM reader has its own line grammar, scale conversion and intermediate allocations; managed header recognition does not prove native decoding support or bound that memory.

scale 后只消费一个空白字节。CR 分隔符后的 LF 已是首个 raster 字节，后续空白或 `#` 均不会再作为头部跳过。保留字段前或紧接 scale 的 PNM 风格注释兼容扩展，注释以 CR 或 LF 结束；这不是标准 PFM 功能。只有 checked 的 `width * height * channels * 4` 运算及精确延伸到输入末尾的 raster，才证明单帧、累计像素和编码存储量。截断、多余字节、拼接图像或算术溢出使完整性保持未知，同时保留已证明的头部。metadata/ICC 长度、float 样本有效性、方向/色彩语义、native 分配和最终 `Mat` 精度仍未知。OpenCV native PFM reader 有自己的行语法、scale 转换和中间分配；托管头部识别不证明 native 解码支持，也不约束其内存。

69 个 PFM 回归用例覆盖所有严格前缀、精确/多余 raster 长度、六种分隔符后的全部首字节、错误/超长 scale、checked geometry、byte[]/Span/Stream 预算及确定性 mutation；旧解析器有 15 个用例失败。8 份嵌入文件固定长度和 SHA256，NumPy 2.3.5 独立核对每个 float 样本和两种字节序，Netpbmfile 2026.10.15 额外解码其中 6 份常规文件。CR/LF 像素与 TAB/`#` 像素文件使用 NumPy 精确字节验证，因为 Netpbmfile 的头部正则不能保留这些边界。两个参考库均不是项目依赖。含 131k 字符 scale 的 byte[] 输入连续识别 8 次，托管分配低于 32 KiB；这属于解析器证据，不是 native 内存上限。

Radiance HDR requires exactly one `FORMAT=32-bit_rle_rgbe` or `FORMAT=32-bit_rle_xyze` assignment and a complete resolution line containing two distinct signed X/Y axes with positive Int32 counts. Duplicate FORMAT lines, even identical ones, or unsupported values keep header facts unknown. FORMAT value whitespace, LF/CRLF lines, long comments and all eight axis/sign orders are supported. X and Y determine logical width and height; the first axis counts scanline records and the second gives their length. The parser scans fixed state without a token string or an allocated scanline. These rules follow the picture section of [Radiance File Formats](https://radsite.lbl.gov/radiance/refer/filefmts.pdf) and the official [header.c](https://github.com/LBNL-ETA/Radiance/blob/master/src/common/header.c), [resolu.c](https://github.com/LBNL-ETA/Radiance/blob/master/src/common/resolu.c) and [color.c](https://github.com/LBNL-ETA/Radiance/blob/master/src/common/color.c) readers.

Radiance HDR 要求唯一的 `FORMAT=32-bit_rle_rgbe` 或 `FORMAT=32-bit_rle_xyze` 声明，以及含两个不同 X/Y 有符号轴、正数 Int32 计数的完整 resolution 行。重复 FORMAT（即使相同）或不受支持的值使头部事实未知。支持 FORMAT 值首尾空白、LF/CRLF、长注释和全部八种轴序/符号组合。X/Y 决定逻辑宽高，第一个轴计数 scanline record，第二个轴给出 record 长度。解析器使用固定状态，不分配 token 字符串或 scanline。规则依据 [Radiance File Formats](https://radsite.lbl.gov/radiance/refer/filefmts.pdf) 的 picture 章节，以及官方 header.c、resolu.c 和 color.c reader。

Each scanline independently selects flat/old-repeat or component RLE encoding. Old `1,1,1,count` markers repeat a preceding pixel from that same record; successive count bytes carry higher powers of 256. Checked remaining-length comparisons and a saturating shift prevent oversized runs, cross-record reuse and integer shift wrap without expanding pixels. Modern `2,2,lengthHi,lengthLo` records require the second-axis length below 32768, four complete component streams, literal counts 1..128 or repeat counts 1..127, and exact packet boundaries. Short modern records are recognized as encoded facts even where OpenCV's reader selects its flat path. Zero-length modern packets keep completion unknown. Single-frame, cumulative-pixel and encoded-storage facts require all declared records and exact EOF; truncated, overlong or concatenated payloads preserve a proven header while completion stays unknown.

每条 scanline 独立选择 flat/旧式重复或 component RLE 编码。旧式 `1,1,1,count` 仅重复同一 record 中已有的像素，连续计数字节按 256 的更高次幂累计。剩余长度比较和饱和 shift 检查阻止超长 run、跨 record 借用与整数移位回绕，不展开像素。新式 `2,2,lengthHi,lengthLo` 要求第二轴长度小于 32768、四条完整 component stream、1..128 个 literal 或 1..127 次 repeat，以及精确 packet 边界。短的新式 record 也可证明编码事实，而 OpenCV reader 在该长度可能走 flat 路径；零长度新式 packet 的完整性保持未知。只有所有声明 record 与精确 EOF 同时成立，才证明单帧、累计像素和编码存储量。截断、超长或拼接负载保留已证明的头部，完整性保持未知。

PAM requires its own complete line-based header: P7 followed by LF (CRLF is accepted as a compatibility form), exactly one positive WIDTH, HEIGHT, DEPTH and MAXVAL, and a terminated ENDHDR with no value. MAXVAL is at most 65535; geometry and tuple depth fit positive Int32. Numeric tokens have no extra data; unknown keywords, duplicate fields (even identical values), empty TUPLTYPE and embedded non-text tuple bytes invalidate all header facts. Leading/trailing header whitespace, blank lines, and standalone comments are allowed. Inline numeric comments are not part of the PAM grammar. This follows the [Netpbm PAM specification](https://netpbm.sourceforge.net/doc/pam.html), with duplicate-field and unknown-keyword behavior cross-checked against OpenCV 5's PAM reader; upstream sources are unchanged.

PAM 要求完整且按行解析的头部：P7 后跟 LF（兼容接受 CRLF），正数 WIDTH、HEIGHT、DEPTH、MAXVAL 各恰好一次，以及不带值且有换行终止的 ENDHDR。MAXVAL 不超过 65535，宽高和元组深度限制在正数 Int32。数值 token 不可附加其他数据；未知关键字、重复字段（包括相同值）、空 TUPLTYPE 及元组文本中的非文本字节使全部头部事实未知。允许行首/行尾空白、空行和独立注释行；数值后的行内注释不属于 PAM 语法。依据 [Netpbm PAM 规范](https://netpbm.sourceforge.net/doc/pam.html)，并与 OpenCV 5 PAM reader 交叉核对重复字段与未知关键字规则；未修改上游源码。

DEPTH alone supplies the encoded channel count, including arbitrary tuples with more than four samples. TUPLTYPE may be absent or occur multiple times; its text describes meanings and is not used to infer channels, color, alpha, or subformat validity. MAXVAL implies one- or two-byte unsigned storage, including byte storage for black-and-white PAM. The parser scans comments/tuple text without copying, concatenating or allocating from declarations. A complete header remains known when checked `width * height * depth * bytesPerSample` overflows, truncates, or fails to reach exact EOF; frame/cumulative/estimated-storage facts then remain unknown. ENDHDR's LF is consumed once and every subsequent byte belongs to the raster, even whitespace or '#'. Metadata/ICC lengths, sample values, tuple semantics, final Mat precision and peak/cumulative native allocations remain unproven. OpenCV's native PAM reader supports only 1..4 channels; header facts for other depths do not claim native decoding support.

编码通道数仅由 DEPTH 决定，包含超过四个样本的任意元组。TUPLTYPE 可以缺省或重复，其文本只描述含义，不用于推断通道、颜色、alpha 或子格式有效性。MAXVAL 决定一个或两个字节的无符号存储，黑白 PAM 也按字节存储。解析器扫描注释/元组文本但不复制、拼接或按声明分配。完整头部可在 checked 的 `width * height * depth * bytesPerSample` 溢出、截断或不能精确到达 EOF 时保留；此时帧数/累计像素/存储估算未知。ENDHDR 的 LF 只消费一次，此后每个字节均属于 raster，包括空白或 '#'。metadata/ICC 长度、样本值、元组语义、最终 Mat 精度及 native 峰值/累计分配仍未证明。OpenCV native PAM reader 仅支持 1..4 通道；其他 DEPTH 的头部事实不代表 native 可解码。

For PNM P1–P6, positive decimal dimensions and a 1..65535 MAXVAL (except PBM) determine encoded depth/channel header facts. Comments end before either CR or LF. Plain PBM (P1) stores individual `0`/`1` bytes: adjacent `0101` represents four pixels, while `00` cannot collapse into one integer sample. P2/P3 use whitespace/comment-separated decimal samples bounded by MAXVAL. Exact standalone completion requires the checked sample count with only whitespace/comments afterward; P4 requires `(width + 7) / 8` bytes per row, and P5/P6 require checked 8- or big-endian 16-bit sample bytes.

对于 PNM P1–P6，正十进制宽高和 1..65535 的 MAXVAL（PBM 除外）决定编码位深/通道头部事实。注释在 CR 或 LF 之前结束。纯文本 PBM（P1）逐个存储 `0`/`1` 字节：连续 `0101` 为四个像素，`00` 不能合并成一个整数样本。P2/P3 使用空白/注释分隔的十进制样本，并限制到 MAXVAL。精确单图完整性要求 checked 样本数且尾部只能是空白/注释；P4 每行要求 `(width + 7) / 8` 字节，P5/P6 要求 checked 的 8 位或大端 16 位样本字节。

Raw P4/P5/P6 consume exactly one whitespace byte after the last header number or its immediately attached comment. A CR delimiter followed by LF therefore has an LF-valued first raster byte; unlike PAM, the raw delimiter is not a CRLF text line. Additional whitespace is never skipped as padding. Truncation, trailing bytes, concatenated images and checked size overflow keep frame/cumulative/storage facts unknown while preserving independently proven header facts. Raw Netpbm permits image sequences and plain PBM permits trailing junk; this API conservatively proves only standalone completion and does not reject the input merely because completion is unknown. Raw sample values, PBM padding bits, gamma/color semantics, native decoding and final/peak native allocation are not validated. The pixel estimate rounds each encoded sample to a byte, so PBM estimates are not packed raster lengths. See the [PBM](https://netpbm.sourceforge.net/doc/pbm.html), [PGM](https://netpbm.sourceforge.net/doc/pgm.html), and [PPM](https://netpbm.sourceforge.net/doc/ppm.html) specifications and OpenCV 5's unchanged `grfmt_pxm.cpp` reader.

raw P4/P5/P6 在最后一个头部数值或其紧接注释之后，只消费一个空白字节作为分隔符。CR 分隔符后若为 LF，LF 已是首个 raster 字节；它与 PAM 的 CRLF 文本行不同。绝不把额外空白当成 padding 跳过。截断、尾部字节、拼接图像和 checked 尺寸溢出使帧/累计像素/存储事实未知，独立头部事实仍保留。raw Netpbm 允许图像序列，纯文本 PBM 允许尾部杂项；此 API 保守证明精确单图完整性，不会仅因完整性未知就拒绝输入。不校验 raw 样本值、PBM padding bit、gamma/色彩语义、native 解码及最终/native 峰值分配。像素估算将每个样本向上取整到字节，因此 PBM 估算不等于位打包 raster 长度。已交叉核对 Netpbm PBM/PGM/PPM 规范和 OpenCV 5 的 `grfmt_pxm.cpp`，未改上游源码。
